# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RuttEtraWeb is a browser-based recreation of the 1973 Rutt/Etra Scan Processor analog video synthesizer. It runs entirely client-side (no backend): webcam / screen / video-file / synthesized-pattern input → scan-line mesh displaced in Z by brightness → free-flight 3D camera, post-FX, recording, WebRTC/WHIP streaming, WebXR, and stereoscopic output. It speaks Web MIDI, multi-band FFT audio reactivity, OSC over WebSocket, gamepad, and bidirectional CV (control voltage) through DC-coupled audio interfaces.

Stack: Vite + vanilla TypeScript (no framework), three.js, PeerJS, hls.js, qrcode. GLSL shaders are imported as assets (`assetsInclude` in `vite.config.ts`). Fully static `dist/` output, deployed to Hostinger via FTP on push to `main` (`.github/workflows/deploy.yml`). PWA/service-worker support was deliberately removed (stale-cache problems); `public/sw.js` is a kill-switch that unregisters old installs — do not reintroduce a service worker.

## Commands

```bash
npm run dev          # Vite dev server on http://localhost:5173
npm run build        # tsc --noEmit && vite build
npm run typecheck    # tsc --noEmit only
npm test             # vitest run (all tests)

npx vitest run -t "pattern of test name"               # by test name
```

`tools/osc-bridge/` is a separate Node workspace with its own `package.json` (`npm install && npm run dev` inside it) — a UDP↔WebSocket bridge so the browser can talk OSC to TouchOSC/Max/SuperCollider. `tools/cv-bridge/` holds reference Python scripts (Raspberry Pi ADCs → OSC).

### Testing conventions

Vitest runs in the `node` environment with an explicit `include` allowlist in `vitest.config.ts` — only pure, DOM-free modules are tested (no three.js/WebGL mocking). **If you add tests in a new directory, you must add its glob to that allowlist or the tests silently won't run.** For DOM-dependent tests, declare `// @vitest-environment jsdom` at the top of the file (see `src/renderer/__tests__/XRManager.test.ts`).

## Design principles (mandatory)

`.cursor/rules/principles.mdc` is the directive form of nine project principles; `PRINCIPLES.md` is the long-form reference; `docs/about/02-design-principles.md` is the artist-facing version. All three cover the same nine principles in the same order. Treat them as constraints, and surface conflicts with user requests rather than silently working around them. The most operationally important:

1. **One concept, one authoritative source.** `Settings.internalBpm` is THE bpm (Classic LFOs, Timeline, Graph clock nodes all read it). `PARAM_DOCS` (`src/ui/help/paramDocs.ts`) drives both in-app Help and the About page's Param Reference. The graph node registry (`src/modulation/graph/registry.ts`) drives both runtime and the auto-generated Node Catalog. `migrateSettings()` is the single migration entry point. `ResolutionManager` is the single sizing authority. Before adding state, search for the existing concept.

2. **Base/live split.** Every modulatable parameter has a base value (what the UI knob shows; `Settings.get/set`) and a live value (what the renderer reads; `liveValues.get(key)`). UI writes base only; modulation engines write contributions to `LiveValuesStore` only; shaders read live only. **Never** `settings.set(key, liveValue)` from any modulation lifecycle — that's the pre-v9 "sticky param" bug.

3. **No silent fallbacks.** If a configured mode's prerequisite is missing (MIDI clock absent, device disconnected, AC-coupled interface), surface the state in the UI and hold last-known behavior. Never auto-substitute a default when a specific mode is selected.

4. **Audio/CV output safety stack (non-negotiable).** Anything that makes sound or sends voltage: defaults disabled, quiet defaults (−18 dB / 0V), soft-start ramps, hard limiter, isolated `AudioContext`, mic-feedback detection. `migrateSettings()` structurally forces `sonification.enabled = false`, `cvOutputEnabled = false`, and every CV channel disabled on **every** load, regardless of saved values. Reference implementations: `src/audio/Sonification.ts`, `src/audio/CVOutput.ts` + `cv-out-worklet.js`.

5. **Coexistence over replacement.** Classic ModMatrix and GraphEngine both exist (`Settings.modMode: classic | graph | both`). Pattern Generator is a compositing layer, not a fourth `sourceKind`. Presets / Timelines / Projects are three separate save formats with different scopes.

6. **Migrations are explicit.** Any saved-format change bumps the version (`_v` for Settings/presets — currently 29 in `src/state/Settings.ts`; `formatVersion` for projects) and adds an idempotent step to `migrateSettings()` / `migrateProject()`. Files with a newer version than the code log `console.warn` and normalize on save — never silently truncate.

7. **Documentation lands with the feature.** New modulatable Settings key → entry in `PARAM_DOCS`. New graph node → complete `NodeDef` in the registry (auto-appears in the About Node Catalog). User-facing behavior change → update `src/ui/help/content.ts` and the relevant `docs/about/*.md`. Docs are part of the feature, not a follow-up.

8. **Smallest working scope first.** Propose the minimum end-to-end version before maximalist scope.

## Architecture

### Entry and bundle strategy

`src/main.ts` routes between synth mode (default) and viewer mode (`?view=<peerId>` — fullscreen PeerJS stream viewer with no UI). Subsystems split into an always-on core (renderer, scene, panel, camera) and lazy modules loaded via dynamic `import()` (timeline, MIDI, audio FFT, OSC, recorder, broadcaster, help) to keep the initial gzipped bundle under ~400 KB. `src/io/IoSubsystems.ts` boots the I/O stack (MIDI clock/manager/mapping, FFT + beat detector, OSC client, CV in/out, gamepad) in its own chunk.

It's a **multi-page build**: `index.html` (synth) and `about.html` (long-form manual). The about page must ship zero synth runtime — no three.js, Web Audio, or PeerJS — enforced by `scripts/check-about-bundle.cjs`. Manual content lives as markdown in `docs/about/` and is rendered to HTML at build time by the `aboutMarkdown` Vite plugin (import suffix `?aboutMd`); `src/about/autogen.ts` builds the Param Reference and Node Catalog from `PARAM_DOCS` and the graph registry.

### Data flow (per frame)

```
video source (webcam/screen/file) ──┐
pattern layer (PatternRenderer) ────┴→ compositor → DCU shader (ruttEtra.vert/.frag)
                                                     ↑ uniforms read liveValues.get(key)
Settings (base values, flat keys) ──→ LiveValuesStore ←── ModMatrix.tick() (Classic slots)
                                          ↑            ←── GraphEngine.tick() (node graph)
        MIDI / OSC / FFT / beat / CV-in / gamepad / pattern-signal-bus feed both engines
```

- **`src/state/Settings.ts`** — typed store of every user-facing parameter, flat dot-free keys (usable as modulation/MIDI/OSC targets), subscribe/notify, versioned `migrateSettings()`.
- **`src/modulation/LiveValues.ts`** — computes `base + sum(offsets) * product(factors)` per namespace; contributions absent from a frame's `setContributions` call are cleared the same frame.
- **`src/modulation/ModMatrix.ts`** (Classic 4-slot engine) and **`src/modulation/graph/GraphEngine.ts`** (node-graph engine; ~40 node types under `graph/nodes/`, registry in `graph/registry.ts`, topo sort in `graph/topo.ts`). Shared output shaping in `modulation/outputStage.ts`.
- **`src/renderer/RuttEtra.ts`** — the scan-line mesh scene. `Postfx.ts` (feedback/bloom/CRT), `CameraRig.ts` (orbit + fly), `ResolutionManager.ts` (sole owner of renderer/postfx/pattern render-target sizing and canvas CSS). `XRManager.ts` (WebXR, v11), `AnaglyphRenderer.ts` and `record/StereoCompositor.ts` (stereoscopic, v12) — XR/anaglyph/stereo paths bypass the EffectComposer.
- **`src/renderer/patterns/`** — Pattern Generator layer: 16 fragment-shader patterns + oscilloscope mode, composited over the video source with 8 blend modes. Each pattern has a GLSL shader **and** a CPU mirror function in `PatternRegistry.ts` (intentional computation duplication — same param source) that publishes signals to `PatternSignalBus` for use as modulation sources.
- **`src/project/`** — Project (`.synth.json`) = full workspace (settings snapshot + presets + timelines); Preset (`.preset.json`) = a look; Timeline (`.timeline.json`) = a score. `Project.ts` is pure helpers; `ProjectStore.ts` handles dirty tracking / recent list / FS Access API with download fallback; `AutoSave.ts` + `RecoveredSession.ts` handle crash recovery. `applyProject()` always routes through `migrateSettings()` so the safety stack applies.
- **`src/ui/`** — vanilla-DOM control panel: `ControlPanel.ts` shell with Synth / I/O tabs, one file per panel section in `ui/sections/`, shared widgets in `ui/widgets.ts` / `ui/shared/SlotRow.ts`, responsive layout system in `ui/layout/`, timeline dock in `ui/timeline/`, graph editor (Beginner + Advanced views) in `ui/graph/`. CRT/phosphor theme in `panel.css` — see `docs/design/panel-design-system.md` for the row/grid layout contract before adding a new widget or row shape (it exists because a slider silently stopped filling its row once, from not having this written down). `ui/tooltip.ts` + `ui/help/sectionHints.ts` drive the panel's delayed hover tooltips (param rows from `PARAM_DOCS`, section headers from `SECTION_HINTS`).
- **`src/audio/`** — FFT analysis, beat detection, CV input/output (AudioWorklets in plain `.js`), Sonification (mesh → audio voice), MeshAnalyzer (8 stats from the `VideoTap` lo-res readback).
- **`src/stream/`** — PeerJS broadcaster/viewer and `WhipPublisher.ts` (WHIP → OBS/MediaMTX/Cloudflare).
- **`src/renderer/RenderPopout.ts`** — pops the render canvas into its own draggable window for two-screen performance rigs (companion to `src/ui/PanelPopout.ts`, which pops the *control panel* instead). Feeds the popup a `canvas.captureStream()` into a `<video>`, deliberately NOT `adoptNode`-ing the canvas itself — a live WebGL context does not reliably survive being moved to another window's browsing context, unlike the plain DOM `PanelPopout` moves.

### State of the REAL cable-alignment fix (2026-07-14, branch `skeuomorphic`) — supersedes the two passes above

The owner reported cables still misaligned (patchproblem3/4, in `~/Pictures`) after two curve-shape passes. Both earlier passes were real improvements but neither was the reported bug — **the drawn endpoint coordinates were always mathematically correct, and every earlier verification ran at text scale 100%, where the actual bug is invisible.** The owner runs Global Text Size at 110%. Root causes (two, both in canvas sizing, not curve or coordinate math — found by instrumenting `bezierCurveTo`/`arc` calls and comparing against the endpoints' true visual rects, which matched exactly):

1. **CSS-zoom scale mismatch** — all three cable canvases (`PatchBayView`, `RackLayer`, graph `CableLayer`) did `canvas.style.width = rect.width + 'px'`, but that style resolves in CSS pixels INSIDE the text-scale `zoom`, so the canvas rendered `zoom×` larger than the region it measures against; every drawn coordinate visually landed at `zoom×` its intended position from the top-left (patchproblem3's endpoints sat at exactly 1.1× the true jack coordinates — the giveaway). "Breaks when resizing" was this too: the misalignment magnitude tracks layout size.
2. **Scrollport-slice clipping (pre-existing, unmasked by the investigation)** — the bay's canvas covered only `.rw-pb-surface`'s border box (scrollport-height) while the module content overflows it far below; cables to jacks below the fold drew into clipped space and vanished entirely.

Fix: `fitCableCanvas()` in `src/ui/cableDraw.ts` (shared by all three surfaces): sizes a cable canvas so its VISUAL size equals an explicit `coverage` rect and sets the transform so one drawing unit = one visual pixel. Two hard-won invariants encoded in its docs:

- **Measure zoom from the canvas's own ancestor chain** (accumulated computed `zoom` walk), never from a host element's box ratio — the zoom boundary (`.rw-zoomchrome > *`) sits at each workspace shell, so the rack overlay's canvas (a direct child of the shell) is itself zoomed while the shell's own box is not; inferring zoom from the shell reads 1.0 and mis-sizes the canvas.
- **`coverage` must never be derived from a scroll extent that includes the canvas itself.** An intermediate version of this fix used `host.scrollWidth`, and since the rack canvas is inside (and zoomed within) `panelRoot`, its own box fed back into its next size — growing ~1.1× per FRAME until a 35,019×92,205px canvas failed to allocate and Chromium painted the whole panel opaque white. `PatchBayView` now computes coverage as the union of the surface's non-canvas children rects (covers the below-the-fold content, board zoom, and free-mode breakout units); RackLayer/CableLayer pass their box. A `MAX_BACKING_PX = 8192` cap with transform compensation makes any future sizing bug degrade to soft cables instead of a white wall.

Verified at text scales 0.8/1.0/1.1/1.3 (endpoint-vs-jack rect instrumentation + screenshots), through window resize drags, bay scroll, bay board-zoom 144%, the rack panel overlay, and the graph editor's port cables — plus a 4s soak per scale asserting the rack canvas backing store stays byte-identical (feedback-loop regression guard). **Meta-lesson recorded**: when a bug report says "still broken" after a pass that verified clean, suspect the ENVIRONMENT DELTA between the owner's setup and the test setup first (here: text scale ≠ 100%) — not another iteration of the same theory.

Implemented node-to-node wiring as a first-class Patch Bay concept, distinct from a `TargetBinding` (which feeds a Settings param):

- `src/ui/rack/rackGeometry.ts` gained `NodeWire` + `nodeWires(patch)` (every currently-wired `GraphNode.inputs[port]` ref, resolved via the shared `splitInputRef` parser — the same one the engine/topo-sort/Advanced-editor use) and `applyNodeInputRef(patch, nodeId, port, ref)` (wire or unplug one port; `ref` follows the engine's own "plain id = default output, `nodeId#port` = named output" convention).
- **"Active" now includes transitive input-feeders**: a node that only feeds ANOTHER active node's input (e.g. a Sync driving a Noise's `clock`, neither directly bound to a param) now gets a module too — `rebuildGraphModules()` does a cycle-safe BFS closure over `node.inputs` starting from the directly-bound set, so "the patch reflected accurately" (the original ask behind the graph-node-visibility feature) extends to feeder chains, not just directly-bound nodes.
- Each active module renders an **IN row per input port the node's type defines** (`getDef(type).inputs`, e.g. Ramp's `trigger`, Noise's `clock` — most node types define none, so most modules show none), above its OUT rows. Draggable both ways, mirroring the existing param-cable gestures: `dragGraphIn` (grab an IN jack — wired or not — snap to any active node's OUT jack to wire it, or drop in space to unplug) and `dragGraphOut` (grab an OUT jack, drag onto an IN jack to wire it; dropping in space does nothing, since one OUT can fan out to many connections — there's no single "the" connection to remove). Both write through `applyNodeInputRef` + `settings.set('modGraph', ...)` + `getEngine().setPatch(...)`, the same two-write pattern every graph-editing surface uses. A node's OUT jack itself still isn't retargetable-by-dragging (same reasoning as the param-binding OUT jack) — only IN jacks are the "move this connection" end.
- New `NODE_WIRE_COLOR` (amber, `#ffb347`) distinguishes node→node wires from node→param bindings (cyan) and Classic cables (green) in the Patch Bay's cable-draw loop; the pending-drag rubber-band and the existing-wire skip-while-dragging logic both extended to the two new `Pending` kinds (`to-graphin`/`to-graphout`).

**A real bug caught live, not by any unit test**: the first version gated IN-row creation on `if (!mod)` (module just-created) — reasoning that "a node's type never changes after creation," so a node's input ports are knowable once and done. That assumption is **false**: Beginner view's source dropdown mutates an *existing* node's `type` in place when you retarget it (same id, e.g. LFO → Noise — `BeginnerView.ts`'s `adapter.source.set`), so a module created while its node was still an LFO (zero inputs) never got the "clock" row added after retargeting to Noise, even though `def.inputs` correctly reported it from that point on. Caught by retargeting a Beginner row from LFO to Noise via Playwright and finding the resulting Patch Bay module had no clock row at all; root-caused with a temporary debug log showing the exact moment `type` flipped while `alreadyHasMod` stayed `true`. Fixed by reconciling IN rows every rebuild (add/remove diffed against the node's *current* type's `def.inputs`, same pattern the OUT-row reconciliation already used) instead of building them once at creation — new rows insert right before the first OUT row so IN visually stays above OUT regardless of which rebuild pass added them.

Also hit, and worked around rather than fixed (**out of scope, flagged for later**): restoring a saved Project via the autosave-recovery flow (`AutoSave`/`projectStore.openFromText`) does not reliably prime the graph node registry before the Patch Bay's first render — unlike `loadSamplePatch()` (File ▸ Load Sample Patch), which explicitly `await`s `ensureGraphEngine()` before writing `modGraph`, project recovery just writes `Settings` directly. Graph node labels can render as raw lowercase type strings (`"lfo"` instead of `"LFO"`) and never self-correct (the signature-gate skips re-render once set, even after the registry loads later). Reproduced with a bare `lfo`-only patch via the recovery path — confirms it's not specific to any node type, purely a load-order gap in the recovery flow. Live verification of THIS feature was done instead via the real user flow (Load Sample Patch → Beginner view retargeting → Advanced view/Patch Bay wiring), which sidesteps the gap entirely and is also the more realistic path anyway.

Verified live (Playwright), all with zero console errors: Noise's "clock" IN row renders correctly and shows unplugged by default; dragging Sync (V)'s OUT jack onto Noise's clock IN jack wires it (both jacks light up plugged, an amber cable renders between them, distinct from the cyan param-binding cables also visible in the same shot); dragging the now-wired clock jack into empty space unplugs it (jack unlit, cable gone). Full suite (540/540, 4 new `rackGeometry.test.ts` cases for `nodeWires`/`applyNodeInputRef`), typecheck, build, and the about-bundle guard all clean.
